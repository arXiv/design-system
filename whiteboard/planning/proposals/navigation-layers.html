Navigation layers, tested on arXiv pages

Shamsi's hypothesis: internal navigation on top, tabs second, filters third. This page tests it on eleven real cases and drafts guidance an agent can reason with.

Summary

  • The order holds; the depth does not. When a page uses more than one, they stack in that order. Every case used one or two; none needed all three.
  • The three layers answer three questions. Which page or task (navigation). Which view of this subject (tabs). Which slice of the data (filters). Classifying by question worked on every case; classifying by level did not.
  • Tabs were the rarest layer. Only the Admin Console user page needs them. In Christopher's dashboard, the second row of tabs holds content people want to see together, so it becomes sections.
  • Five needs fall outside the model: where in this page (TOC bar), the next item in a queue (stepper), the step in a sequence (submission), the mode of a page (view or edit), and settings that change a calculation (threshold days). The guidance needs to name them so agents do not force them into tabs or filters.
  • One real strain: navigation with many destinations. The Admin Console has 18 pages in 6 groups. A horizontal bar cannot hold that. This needs a decision (below).

Draft guidance

As it might appear on a docs page, "Organising complex pages", with a short pointer in AGENTS.md.

Questions, with signals

  1. Does the user move to a different task or page? Navigation. A few sections: the secondary bar. Many destinations in groups: see decision 3.
  2. Does the user switch between peer views of one subject, one at a time? Tabs. Not tabs when people compare the views, search across them, print them or link to one part: use sections on one page.
  3. Does the user narrow the same content? Filters. Put them above everything they change. If people will share a filtered view, write the choices to the address.
  4. Does the user change how a number is calculated? A setting, not a filter. Group it with the filters under "Settings", and state its value where the numbers are.
  5. Is the content one long page? Sections and a TOC bar, not tabs.
  6. Does the user work through items one at a time? A stepper.
  7. Must the user complete steps in order? A sequence with step status (to be designed with the submission work).
  8. Does the user switch between viewing and editing? A mode control, not tabs.

Use only the layers the content raises. When several apply, stack them in this order from the top: navigation, tabs, filters.

Guardrails (from failures seen)

  • One control of each kind per view: one navigation bar, one row of tabs, one filter bar.
  • Tabs never sit inside a tab panel.
  • Filters apply to everything below them, and only to that.
  • One Apply button per filter bar.
  • No breadcrumb on a page that has secondary navigation.

Worked examples

The membership dashboard, the Admin Console user page, arXiv Check and the paper reader, as above: what each user decides, which question it answers, and the result.

Where it should live

  • A new docs page, "Organising complex pages", under Organizing content: the questions, the guardrails and the worked examples with rendered sketches. Its digest goes in docs/spec/, so agents read it.
  • AGENTS.md: one routing row ("a page with several kinds of choice") pointing to it, and one line telling agents to classify each choice by question before picking a component.
  • DESIGN-POLICIES.md: the guardrails only, since they are firm. The questions stay guidance.

Decisions for Shamsi

  1. Adopt the three questions (navigation, view, slice) as the model, with "only the layers the content raises" instead of a fixed depth?
  2. Name the five needs outside the model (TOC bar, stepper, sequence, mode, settings) in the guidance?
  3. Many destinations (the Admin Console's 18 links in 6 groups): a grouped navigation list in the sidebar position for internal tools (this reverses "the sidebar never holds section navigation" for that case), or grouped dropdowns in the header like these docs, or both by size?
  4. The dashboard scope selects (group, archive, category): a filter bar that writes to the address, so one group can be linked?
  5. Moderation and Administration move out of the user portal's bar into the internal tools?
  6. Create the "Organising complex pages" docs page, the AGENTS.md row, and the guardrails in DESIGN-POLICIES?
  7. A filter bar component (fields, one Apply button, on the warm tint) as the next build, before the dashboard rebuild?
