Versions

How a paper shows its submission date, its current revision date, and its version history — below the title, on the abstract page and in staff tools. Prior versions are inline text links; the version being viewed is bold, not a link. The same treatment scales from one version to twenty. Reference implementation: abstract-redesign.html. Spec: CONTEXT.md (Versions).

One version — near-silent

The common case: most papers have a single version. Show the submission date and nothing else — no "revised", no "(this version)", no version links to disambiguate.

A few versions — viewing the latest

Once a paper has more than one version, the date row carries both dates: Submitted is always the v1 date; Revised … (this version) is the date of the version you're reading. Prior versions follow as Link Blue links; the current one is bold, not a link, and carries aria-current.

Many versions — unbroken

The date grammar is identical no matter how many versions exist — only the inline link list grows, wrapping cleanly at 20+. No separate "many" component, no dropdown, no internal scroll. Monospace with tabular figures keeps the numbers aligned as they wrap.

Viewing an older version

When the reader is on anything but the latest, two things change. The date row reads Submitted … (this version) on v1 — v1 is the submission, so there's no "revised" — and an amber warning appears, pointing to the current version. The warning uses the shared Warning color (never white, never an error red) and stays to one compact row.

Rules that travel with the pattern

Two dates, one grammar

Submitted [v1 date] is always shown. Add · Revised [this version's date] (this version) only once a paper has more than one version. "(this version)" attaches to whichever date belongs to the version being viewed — so on v1 it reads "Submitted … (this version)", on a later revision it reads "Revised … (this version)". Dates use <time datetime>.

Current is bold and aria-current, never color alone

The version being viewed is distinguished by weight and by aria-current — two non-color signals — so it survives grayscale, forced-colors, and screen readers (WCAG 1.4.1). It is deliberately not a link: you can't navigate to where you already are.

Prior versions are inline links, so they're underlined

They sit in a run of identifier text, so link-vs-text contrast can't carry them alone — underlines are mandatory (DESIGN-POLICIES, link underlines). Link Blue --link. Each carries an explicit aria-label ("View version 1").

Older-version warning: amber, compact, advisory

Render it only when the version being viewed is not the latest. Use the shared Warning tokens (--warning-bg / --warning-border / --warning-fg) — amber says "advisory," not error-red and not a blank white box — with the alert-triangle icon inline (never on its own line) and the text to one row. In production this is the .ds-alert warning variant. It links straight to the current version.

One treatment across the whole spectrum

Don't branch into a "few versions" chip row and a "many versions" dropdown. The same inline list wraps from 1 to 20+, and the date grammar never changes. Version numbers render in --font-mono (already tabular) or with font-variant-numeric: tabular-nums so they don't jitter as the list wraps.

Why it's designed this way

Background, if you want it. The affordance has to disappear for the common case and stay unbroken for the rare one — that constraint is what shapes everything above.

Who cares about versions

Authors, publishers, and overlay journals — provenance, and citing or linking a specific version. For them the version and its date must be explicit and addressable.

Who doesn't

Most readers. They want the latest and go straight to reading. The version affordance must never tax them for attention they didn't ask to spend.

The distribution is lopsided

The vast majority of papers have one version; some have two or three; a tiny minority have many. Design for the whole spectrum with one treatment.

So the rule is

Near-silent at one version, scannable at a few, unbroken at 20+ — and always answering the two questions that matter: when was it first submitted, and when was the version I'm reading revised.
