Getting the design system into the dev repos

A staged path — draft for discussion.

This is not a menu of competing options. It is one path in three stages, each building on the last. The destination is an accessibility-led semantic structure contract: a design system that lives in git, ships as versioned code, is enforced automatically, and improves as developers use it. We can't reach it in one step — it depends on first hardening the system and making arXiv's markup semantically sound — so the stages describe what we can do now, soon, and once the HTML is structured. Approaches we considered and set aside are recorded at the end.

Now

Manual reference

design-system repo (prose) → rebuild by hand

Design-system reporead as reference read · drifts→ Agent / devinterprets & rebuilds → Dev repodiverging copy

Includes

  • The repo as a written reference
  • Works on any stack, any agent, today

Gives you

  • Something usable right now, nothing to build first

Still missing

  • Output drifts — no live link
  • Token-intensive: the agent reads the whole prose corpus each time
  • Conformance is unverified

Contract status: none. The design system is re-interpreted from scratch each time, so nothing holds the repos to it.

Soon

Versioned package + discipline + manual checks

tokens.json + plain-CSS package → version-pinned link → human review

Design-system reposource of truth publish→ Versioned packageDTCG tokens + CSS vars link · pin→ Dev repo+ manual review

Includes

  • A versioned, framework-agnostic package: DTCG tokens.json + plain-CSS custom properties
  • An agent-readable spec, restructured (tables, tokens) to cut token load
  • Conformance by human review / checklist

Gives you

  • One source of truth for values, version-pinned (ends the drift)
  • Much lower token load — values are structured, not prose
  • A shared semantic token vocabulary begins

Requires first

  • Fix the version contract (one deterministic pin across repos)
  • Stabilize the token + naming foundation
  • Structure the design-system content

Contract status: emerging. A shared vocabulary plus manual accessibility review make it begin to be a semantic structure contract — but not all the way, because the consuming markup is still inconsistent and enforcement is human.

Later

Verified contract — once the HTML is structured

versioned package + automated tests/linting in CI + two-way contribution loop

Design-system repospec + checks publish→ Package + checkstokens, CSS, lint rules link→ Dev repoagent builds, CI verifies ← PR (improvements)

Includes

  • Everything in Soon, plus…
  • Automated conformance: linting + tests in CI (contrast, palette/font allowlists, :focus-visible, semantic-structure checks)
  • A two-way contribution loop with trust-level governance (mechanical fixes auto-merge; spec changes are reviewed PRs)
  • An agent-agnostic entry point (AGENTS.md beside CLAUDE.md) — not locked to one tool
  • Semantically structured HTML across surfaces

Gives you

  • Brand + accessibility fidelity proven automatically across every repo
  • The designer owns the spec and the checks — not every PR
  • Cheap, reliable redesigns: change tokens → agents propagate → checks verify
  • A11y invariants encoded as checks, so no future reskin can regress them

Requires first

  • The markup restructured to be semantically sound (done per-surface, agent-assisted)
  • The design system stabilized and versioned enough to enforce
  • Team capacity to maintain the checks (start small, grow)

Contract status: realized. This is where it comes into its own — the accessibility-led semantic structure contract is real and automatically enforced.

Considered and set aside

Recorded so the team knows these were weighed, not overlooked.

Claude Design as the pipeline Rejected as the backbone

Claude Design imports the system and produces a brand-checked prototype, handed to Claude Code to build as production code.

Why not: it couples our workflow to one vendor's tool, produces prototypes rather than a canonical artifact, and our source of truth must live in git and stay tool-neutral. We keep it in the toolbox as a prototyping and exploration tool (it built the transitional spinout chrome) — just not as the integration path.

Hybrid (split package + agent track) Rejected as redundant

Ship invariants as a partial package; route flexible parts through an agent that prototypes then builds them.

Why not: the staged path already subsumes it — the package is Soon, the agent-built work is Later. As a standalone option it adds complexity without adding a distinct capability.

Folded in, not dropped: the old “manual reference” option is now the Now stage, and the old “package dependency” option is the versioned package inside Soon and Later — so they are no longer listed as separate options.   Claude Code — Anthropic's coding agent that builds against the repo and (in Later) runs the checks. The git design-system repo stays the spec / source of truth throughout.
