PROPOSAL — a lozenge component (not built; recommendation only)

Asked by Shamsi 2026-08-11: do we have a lozenge/pill component, and should it be refined with color variants by prominence? Researched across both stylesheets, every pattern page, every mockup, and the blog theme.

Short answer

No — we have no lozenge component. We have two promoted things that are neither: .ds-element-pill (public) is a floating container that hosts buttons on equations and figures, documented as "the pill itself only provides the floating-panel material"; and .type-badge (internal) is a 3px-radius rectangle locked to one meaning, submission type.

Everything that is actually a labeling pill lives in a mockup or in the blog theme. Nothing is shared. And yes — this is worth fixing, because we are currently maintaining the same idea five times.

What we have today

The same concept — "an arXiv subject category, labeled" — is currently built five different ways, two of them in the same file:

Across the whole inventory there are five different corner radii for the same visual idea — 999px, 22px, 20px, 10px, and a 3px family — and three unrelated type registers (mono 12, condensed-caps 11, sans 13). None of the mockup versions are dark-mode aware. None except the blog's declare a minimum target size.

The blog's .arxiv-lozenge is the one built correctly, and it should be the basis for the component. It is the only one that: draws every value from tokens (so dark mode works for free), sets min-height: 24px for the WCAG 2.5.8 target floor, uses the condensed-uppercase register our type scale already reserves for metadata, and has its color rationale written down ("light blue = arXiv speaking").

Two things found along the way that need your decision

1. Our color docs contradict our stylesheet about lime. color-mapping.md lists Access Lime for public-page use as "small highlights: accent stripe, category marker, 'new' badge" — which sounds like exactly the accent tier a lozenge would want. But the public stylesheet has no lime token at all, and says so deliberately: "Access Lime stays staff-only." Most readers would call a lime badge on a public page a violation of the never-cross rule.

I have not proposed a lime tier below. Either the stylesheet is right and that line should come out of color-mapping.md, or lime genuinely has a tiny public accent role and the rule needs to say so explicitly. It cannot stay ambiguous.

2. Pill-shaped buttons conflict with the button policy. DESIGN-POLICIES sets 6px radius for all buttons. The reader mockups use 20–22px radius on real <button> elements (the "Contents" trigger, the reader toggle, arXiv Check's mode chip). That is a button decision, not a lozenge decision, and it is separate from this proposal — but somebody should make it rather than letting each mockup pick.

Recommendation

Add .ds-lozenge to the public stylesheet, based on the blog's construction, with three prominence levels built entirely from tokens we already own. No new colors.

Level 1 — quiet (the default)

Warm grey. For labels that organize without claiming attention: counts, ancillary tags, anything that is simply true rather than notable.

Rules that would ship with it

  • A lozenge labels or categorizes. It never navigates as its main job. We already decided this once: color-mapping.md retired the filled version pills in favor of inline text links, and the nav pill was rejected the same way. A category lozenge that happens to link to a listing is fine; a lozenge used instead of a link is not.
  • Status colors report a condition, never emphasis. If the label is not about state, it is quiet or chrome.
  • Color is never the only signal — the words say what it means. Existing rule, restated at point of use because this is exactly where it gets broken.
  • Interactive lozenges keep the 24px minimum height and get real hover and focus-visible states. Static ones may be shorter but should not be.
  • The 3px rectangle stays a different thing. .type-badge is shipped, contrast-verified, and lives in dense table cells where a pill wastes width. I would leave it alone and document the distinction rather than force a migration: pill = a discrete labeled object in a wrapping list; rectangle = a compact code in a data grid.

What it would cost

The component itself is about 25 lines of CSS and a section on an existing pattern page — small. The real work is deciding not to hand-build the sixth version next time. Nothing has to migrate at once: the four mockup copies collapse to one class whenever the category-editor pattern page gets built, and the blog swaps .arxiv-lozenge for .ds-lozenge on its next release. Both are follow-ons, not prerequisites.

Open questions

1The lime contradiction above — remove the line from color-mapping.md, or carve out an explicit public accent role for lime?
2Condensed uppercase for words (the blog's register) and mono for identifiers (cs.AI) — right split? The admin mockups currently use mono for everything.
3Is "lozenge" the name we want, given the audience? "Tag" and "label" are plainer; "chip" is what the admin mockups already call it. The class name should be whatever people will say out loud.
4Pill-shaped buttons in the reader — separate decision, but worth settling while this is in your head.
