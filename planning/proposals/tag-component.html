PROPOSAL — a tag component (not built; recommendation only)

Asked by Shamsi 2026-08-11: do we have a tag/pill component, and should it be refined with color variants by prominence? Researched across both stylesheets, every pattern page, every mockup, and the blog theme.

Short answer

No — we have no tag component. We have two promoted things that are neither: .ds-element-pill (public) is a floating container that hosts buttons on equations and figures, documented as "the pill itself only provides the floating-panel material"; and .type-badge (internal) is a 3px-radius rectangle locked to one meaning, submission type.

Everything that is actually a labeling pill lives in a mockup or in the blog theme. Nothing is shared. And yes — this is worth fixing, because we are currently maintaining the same idea five times.

What we have today

The same concept — "an arXiv subject category, labeled" — is currently built five different ways, two of them in the same file:

Across the whole inventory there are five different corner radii for the same visual idea — 999px, 22px, 20px, 10px, and a 3px family — and three unrelated type registers (mono 12, condensed-caps 11, sans 13). None of the mockup versions are dark-mode aware. None except the blog's declare a minimum target size.

The blog's .arxiv-lozenge is the one built correctly, and it should be the basis for the component. It is the only one that: draws every value from tokens (so dark mode works for free), sets min-height: 24px for the WCAG 2.5.8 target floor, and has its color rationale written down ("light blue = arXiv speaking"). Its colors, geometry, and states carry over unchanged. One change from it: the type register moves from condensed to mono (Shamsi 2026-08-11) — mono is arXiv's identifier voice, and most of what a tag holds is an identifier.

Two things found along the way — both now settled

1. Lime does not go on public pages. Resolved 2026-08-11. color-mapping.md used to offer Access Lime for a public "category marker" or "new" badge, which sounded like the loud accent tier a tag would want. But the public stylesheet has no lime token and says so deliberately: "Access Lime stays staff-only." Shamsi's call: "that is crossing the internal/public line." The line is out of the color docs, and there is no lime tag tier.

2. The 6px button radius is not a vestige. Checked 2026-08-11. Every button we have actually documented is 6px — .ds-btn in the public stylesheet, .btn in the internal one, and every button rendered on buttons.html. Nothing documented has overridden the rule, so it is accurate and worth keeping.

The 20–22px radii I flagged are all in mockups — the reader's "Contents" trigger, the reader toggle, arXiv Check's mode chip — and mockups are never a reference. What is genuinely interesting is that three separate explorations independently reached for a pill-shaped button for content-anchored controls. That is a signal worth a decision of its own: either the system gains a documented pill variant for controls that float against content, or those mockups conform to 6px when they are promoted. Not part of this proposal.

Recommendation

Add .ds-tag to the public stylesheet, based on the blog's construction, with three prominence levels built entirely from tokens we already own. No new colors.

Level 1 — quiet (the default)

Warm grey. For labels that organize without claiming attention: counts, ancillary tags, anything that is simply true rather than notable.

on warm wash Preprint 12 requests cs.AI

Level 2 — chrome blue (the workhorse)

The "arXiv is speaking" tint family. For categorizing labels: subject categories, topics, the blog's post categories. This is the blog's current tag, unchanged. Interactive ones get hover and focus states and keep the 24px minimum height.

static Policy Accessibility math.CO
as links Announcements Community ← hover these
removable physics.optics ✕ math-ph ✕

Level 3 — status (only when the label carries state)

Three of the four alert families. A tag earns a status color only when it reports a condition — on hold, withdrawn, valid — never for decoration or emphasis. A state that is merely neutral, like "under review", stays chrome: it is information, not an alert.

Why there is no info tier (Shamsi spotted this by eye, 2026-08-11): the info family and the chrome family are near-twins. Their fills differ by 1.03:1 in light mode and are the identical color in dark — both #132433 — with text differing by only 1.46:1. Two tags meaning different things would have looked the same. Chrome blue already is the informational blue for tags, so the info variant is dropped rather than nudged.

Borders sit in the decorative tier and are never the sole signal — the label's own words carry the meaning, which is the existing rule that color is never the only carrier.

The construction

.ds-tag { display: inline-flex; align-items: center; gap: 5px; min-height: 24px; /* WCAG 2.2 SC 2.5.8 target floor */ padding: 2px 12px; border-radius: 999px; font-family: var(--arxiv-font-mono); /* the identifier register */ font-size: 0.6875rem; font-weight: 500; text-transform: uppercase; letter-spacing: 0.02em; white-space: nowrap; text-decoration: none; background: var(--arxiv-card-grey); border: 1px solid var(--arxiv-border-light); color: var(--arxiv-library-grey); } .ds-tag--chrome { background: var(--arxiv-tint-light); border-color: var(--arxiv-tint-border); color: var(--arxiv-archival-blue); } .ds-tag--success { background: var(--arxiv-success-bg); border-color: var(--arxiv-success-border); color: var(--arxiv-success-fg); } .ds-tag--warning { background: var(--arxiv-warning-bg); border-color: var(--arxiv-warning-border); color: var(--arxiv-warning-fg); } .ds-tag--error { background: var(--arxiv-error-bg); border-color: var(--arxiv-error-border); color: var(--arxiv-error-fg); } /* Opt out of the uppercase default. For identifiers, whose case is part of the data, and for labels long enough that caps slow reading down. */ .ds-tag--keep-case { text-transform: none; letter-spacing: 0; }

Case — when a tag is uppercase

Default: uppercase. Short metadata labels read well in caps and it keeps a tag visually distinct from body text. Two exceptions, both using .ds-tag--keep-case:

  • Identifiers keep their own case — category codes, arXiv IDs, anything where the case is part of the data rather than a styling choice.
  • Long or awkward labels keep their own case. Past roughly three words, or with mixed-case names inside, caps slow reading down. Judgment call, deliberately — a hard character limit would be wrong more often than it was right.

Always apply caps with CSS text-transform, never by typing them. The underlying text then stays correct for copy-and-paste, in-page search, and screen readers, and the same markup can be re-styled later without touching content.

Category names are copied, never restyled. Settled 2026-08-11. An earlier draft of this rule said categories are always uppercase after the last period. Checked against the canonical list in the saved production page in this repo, that holds for 115 categories — and breaks for 31, every physics.* (22) and every cond-mat.* (9) subcategory:

as arXiv publishes physics.optics cond-mat.str-el cs.AI
uppercased physics.optics cond-mat.str-el cs.AI ← first two are not real categories

So the rule is a copy rule, not a capitalization rule: show a category exactly as arXiv publishes it, capitalization included, and never transform it. That is right for all 146 without anything to remember, keeps display matching the URL and the API, and stays correct if the taxonomy changes. It also dissolves a question the earlier version raised — whether any category has two periods — because nothing ever has to find the last one. Category tags always carry .ds-tag--keep-case.

Rules that would ship with it

  • A tag labels or categorizes. It never navigates as its main job. We already decided this once: color-mapping.md retired the filled version pills in favor of inline text links, and the nav pill was rejected the same way. A category tag that happens to link to a listing is fine; a tag used instead of a link is not.
  • Status colors report a condition, never emphasis. If the label is not about state, it is quiet or chrome.
  • Color is never the only signal — the words say what it means. Existing rule, restated at point of use because this is exactly where it gets broken.
  • Interactive tags keep the 24px minimum height and get real hover and focus-visible states. Static ones may be shorter but should not be.
  • The 3px rectangle stays a different thing. .type-badge is shipped, contrast-verified, and lives in dense table cells where a pill wastes width. I would leave it alone and document the distinction rather than force a migration: pill = a discrete labeled object in a wrapping list; rectangle = a compact code in a data grid.

Measured against the real design (2026-08-11)

Shamsi pointed out that category management is already designed, in the user page (privileges accordion) and the paper details edit-metadata modal. Both were measured in the browser against the rules above. Mockups are never a build reference, so nothing here is a defect — the question was whether the design conflicts with the rules. It does not. What it has is three parallel implementations of one thing.

What the mockups teach the spec

These two designs cover states the proposal above does not, and they should shape .ds-tag rather than the other way round:

  • A remove control (✕) inside the tag, with the asymmetric padding it needs.
  • A nested source badge — a small pill inside the tag naming where an endorsement came from. The only pill-in-a-pill anywhere in the system.
  • Drag to reorder: grab cursor, and a lifted, slightly rotated dragging state.
  • A primary marker inside the tag, as text rather than color alone.
  • A negative variant carrying a minus prefix.

What it would cost

The component itself is about 25 lines of CSS and a section on an existing pattern page — small. The real work is deciding not to hand-build the sixth version next time. Nothing has to migrate at once: the four mockup copies collapse to one class whenever the category-editor pattern page gets built, and the blog swaps .arxiv-lozenge for .ds-tag on its next release. Both are follow-ons, not prerequisites.

NameTags, everywhere — class .ds-tag. Shamsi 2026-08-11: "label" is too generic, and "tag" is what people will actually say. Supersedes "lozenge" and the admin mockups' "chip".

Still open

Nothing blocking. The earlier open question — ship now, or wait for a real consumer — is answered: the consumer already exists in the two mockups above, with its states designed. The recommendation is to build .ds-tag against them, repoint all three implementations at it, and let the category-editor pattern page document the editing affordances on top.
