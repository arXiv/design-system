Bulk Action Bar

A contextual toolbar that appears directly above the moderation queue table when one or more submissions are selected. Offers Approve, Hold, and Remove actions on the selection, with an inline confirmation gate on the destructive action and message states for success and failure.

Default — nothing selected

When no submissions are selected the bulk action bar is absent. The queue table renders on its own inside .bulk-action-wrap, which provides the shared outer border and border-radius for both the bar and the table.

Selection active

When one or more rows are selected, the bar appears above the table with the count, a "Clear selection" affordance, and the three bulk actions. Selected rows receive a lime-tint background as a secondary cue alongside the checked checkbox.

Button roles — internal surface: Approve selected uses .btn-primary (Access Lime #c4d82e) — the primary action colour for internal tools (arXiv Check, Admin Console). Put on hold uses .btn-secondary (lime tint). Remove selected uses .btn-destructive (Danger Red #c62828). Open Blue is not used here — it is locked to public pages.
Selection count: aria-live="polite" + aria-atomic="true" on .bulk-count ensures screen readers announce the updated count as the moderator checks and unchecks rows. The element must exist in the DOM before the first count update — do not inject it dynamically.
Clear selection: Uses .btn-link — a <button> styled as an inline underlined link — per design-system.css: "Use for low-emphasis inline actions: Reset to default, Clear all, Show more." It carries no visual weight relative to the action buttons but remains keyboard-reachable and gets a focus ring.

Destructive confirmation

Clicking Remove selected replaces the bar's action group with an inline confirmation prompt. The bar background shifts to the danger tint (var(--error-bg)). This gates the irreversible action against fat-finger mistakes without blocking the viewport with a modal.

Why inline confirm: Per design-system.css destructive button rules: "Always pair with a confirmation step (dialog or inline confirm)." Inline confirm is preferred over a modal when the affected rows are visible in the same view — the moderator can see exactly what will be removed while deciding. A modal would be appropriate if the queue scrolls out of view.
ARIA: role="alert" on .bulk-confirm-msg announces the danger message assertively when the confirm panel appears. JavaScript should move focus to "Confirm removal" on reveal. "Cancel" returns focus to "Remove selected" and restores the bar's default state.

Success state

After an action completes, the bar is dismissed and a .ds-alert-success appears above the (now-updated) table. Uses role="status" for a polite screen reader announcement.

Dismiss: .ds-alert-dismiss (from design-system.css) lets the moderator clear the message after reading. The alert can also auto-dismiss when a new row selection begins.

Failure state

If an action fails — network error, server rejection, partial failure — a .ds-alert-error appears above the bar. The bar remains visible with the selection intact so the moderator can retry or choose a different action. Uses role="alert" for an assertive announcement.

Bar persistence on failure: The selection remains intact. The moderator can retry without re-selecting rows, or pivot to a different action. The error alert and bar coexist above the table.
Assertive vs polite: Failure uses role="alert" (assertive — interrupts immediately); success uses role="status" (polite — waits for the current interaction to finish). This matches urgency to ARIA intent: a failure needs immediate attention, a success does not.
