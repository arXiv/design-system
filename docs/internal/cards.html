Cards

The info card is a read-only metadata panel for displaying system-supplied context (user identity, submission details, IP/date stamps). In light mode it renders as a warm tinted panel with a lime top border; in dark mode it takes the charcoal treatment listed under Spec. Either way its filled surface creates a deliberate visual boundary from editable content areas. The general-purpose card, .ds-card, is documented on Organizing content.

The info card

Each row stacks a label over a value. Values can be plain text, a link, or a monospace ID. The card always reads correctly against both the warm-wash page background and a white content area.

.info-card
The container: a warm tinted surface with a lime top border, holding only .info-card-row children. It sets no width; the sidebar it sits in does. Requires role="region" and an aria-label.
role="region" aria-label="…"
Required on the container. The label names what the card holds, such as “User information” or “Submission information”, and is what a screen reader user hears when jumping to it.
.info-card-row
One label over one value. Rows are separated by a hairline; the last row has none.
.info-label
The field name. Small, bold, and uppercased by CSS, in --ds-text-muted. Type it in sentence case.
.info-value
The value, in IBM Plex Mono. It breaks anywhere, so a long address or identifier wraps inside the card instead of widening it. Every value takes this class, whether it is a plain <span> or a link.
.info-link
A value that navigates to a related record. An <a> with an href, added alongside .info-value: underlined, in the link colour, with the hover and visited colours of every other link.

In context

The card sits in a fixed-width sidebar (240px) alongside the main content area. The tinted surface anchors the page without competing with the editable content.

Accessibility essentials

  • Name the region. Put role="region" and an aria-label on every .info-card, so a screen reader user can jump straight to it and hears what it holds, such as “User information”. A region without a name is not exposed as a landmark at all.
  • Keep each label with its value. A label and its value sit together in one .info-card-row, label first, so they are read as a pair. The label is real text in the markup and the uppercase comes from CSS, so it stays correct for a screen reader and for copy and paste.
  • Monospace values are still text. An identifier, an address, or a date in .info-value is plain text: it can be selected, copied, found with in-page search, and read aloud. Do not put a value in an image or draw it with CSS.
  • No editable fields inside. The card is read-only system context, and its filled surface says so. A form control inside it contradicts what the surface tells a sighted reader and puts a focus stop inside a region that announces as reference. Editable fields take a .ds-card instead.

Rules

Usage rules

  • Read-only only. Never place editable fields inside an .info-card. The filled surface signals “this is system context, not something you control here.”
  • Editable content uses a different container. When a group of editable fields needs a boundary, use a neutral section card — a white panel with a 1px --ds-border hairline and an 8px radius, which is .ds-card — not the .info-card. Keeping the two visually distinct is deliberate: a filled/tinted surface reads as read-only system context; a plain bordered panel reads as “you can edit this.”
  • Sidebar placement. Use at a fixed 240px width in a flex sidebar alongside the main content area. The contrast between the card and the warm-wash page background creates the visual hierarchy.
  • Links in the card. Use .info-link on values that navigate to a related record (user profile, submission detail). Limit links to navigational items — do not use them for inline actions.
  • Monospace IDs. .info-value already renders in IBM Plex Mono at 12px for every value (“monospace signals read-only system data”) — arXiv IDs need no override.
  • Row count. 2–6 rows is the intended range. If more fields are needed, consider grouping into two separate cards or a different layout rather than a very tall single card.

Why lime on dark, not white?

White text on the dark card would create a generic “dark panel” with no connection to the arXiv palette. Lime (#c4d82e) on the dark surface passes AAA contrast (8.4:1) while using the same brand accent as primary buttons and the action bar — reinforcing that this information belongs to the same system.

Why two greens (label vs value)?

The two-tone treatment comes from the admin console pattern: a muted sage label (#cbcdac) that recedes, and a bright lime value that the eye lands on first. The hierarchy guides reading order — label names the field, value delivers the content.

Spec

Dark mode values

These are the dark-mode values (applied when the theme is dark, whether from the system setting or from the theme control in the header). In light mode .info-card uses the tokens in internal-tools.css: #e8e4dc background with a 4px #c4d82e top border, labels var(--ds-text-muted), values #1c1a17, links var(--ds-link). The dark palette below is hardcoded rather than tokenized — intentionally self-contained and only valid on the dark surface.
