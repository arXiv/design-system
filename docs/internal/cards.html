Cards

The info card is a read-only metadata panel for displaying system-supplied context (user identity, submission details, IP/date stamps). In light mode it renders as a warm tinted panel with a lime top border; in dark mode it takes the charcoal treatment shown below. Either way its filled surface creates a deliberate visual boundary from editable content areas.

Variants

Each row stacks a label over a value. Values can be plain text, a link, or a monospace ID. The card always reads correctly against both the warm-wash page background and a white content area.

Color values

These are the dark-mode values (applied under html:not([data-theme="light"])). In light mode .info-card uses the tokens in internal-tools.css: #e8e4dc background with a 4px #c4d82e top border, labels var(--ds-text-muted), values #1c1a17, links var(--ds-link). The dark palette below is hardcoded rather than tokenized — intentionally self-contained and only valid on the dark surface.

Role Value Usage
Card background #2e2b26 Container background — Repository Brown darkened
Row divider rgba(255,255,255,0.07) Hairline between rows — subtle on dark surface
Label #cbcdac Field name — sage-green tint, ~8.6:1 on card bg ✓
Value #c4d82e Plain value text — brand lime, ~8.4:1 on card bg ✓ AAA
Link (rest) #c4d82e Linked value at rest — same as plain value + underline
Link (hover) #d8ee50 Brightened lime on hover
Link (visited) #a8c020 Slightly muted lime — signals page was visited

Usage

  • Read-only only. Never place editable fields inside an .info-card. The dark surface signals "this is system context, not something you control here."
  • Editable content uses a different container. When a group of editable fields needs a boundary, use a neutral section card — a white panel with a 1px #ddd8d2 hairline and an 8px radius (warm border grey — the internal stylesheet defines no border token; the public system names this value --ds-border) — not the .info-card. Keeping the two visually distinct is deliberate: a filled/tinted surface reads as read-only system context; a plain bordered panel reads as "you can edit this."
  • Sidebar placement. Use at a fixed 240px width in a flex sidebar alongside the main content area. The contrast between the dark card and the warm-wash page background creates the visual hierarchy.
  • Links in the card. Use .info-link on values that navigate to a related record (user profile, submission detail). Limit links to navigational items — do not use them for inline actions.
  • Monospace IDs. .info-value already renders in IBM Plex Mono at 12px for every value ("monospace signals read-only system data") — arXiv IDs need no override.
  • Row count. 2–6 rows is the intended range. If more fields are needed, consider grouping into two separate cards or a different layout rather than a very tall single card.
  • Accessibility. Always add role="region" and aria-label on the .info-card container so screen readers can navigate directly to it.

Why lime on dark, not white?

White text on the dark card would create a generic "dark panel" with no connection to the arXiv palette. Lime (#c4d82e) on the dark surface passes AAA contrast (8.4:1) while using the same brand accent as primary buttons and the action bar — reinforcing that this information belongs to the same system.

Why two greens (label vs value)?

The two-tone treatment comes from the admin console pattern: a muted sage label (#cbcdac) that recedes, and a bright lime value that the eye lands on first. The hierarchy guides reading order — label names the field, value delivers the content.
