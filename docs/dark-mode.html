Dark mode

How dark mode works in this system, and what is dark-aware today. The rule that governs everything else: new pages and components are light-only — dark values exist in the stylesheets as foundation, and they flip automatically; nobody hand-picks them.

Checklist: adding or changing a component

In order. Each step links to the reasoning below. If you follow only this list and read nothing else, dark mode will work.

  1. Take every colour from a token. Never write a dark hex into a page or a component. Components that consume tokens flip for free. How it works
  2. Decide whether the colour is content or identity. Content flips. Identity is pinned to a literal with a comment saying why — a masthead, a brand fill, a colour specimen whose subject is the value itself. Trap 1
  3. Fill raised things with --ds-surface. Not --ds-canvas: the wash is a pale tint in light and is the canvas in dark, so anything filled with it disappears. Trap 2
  4. Check any text sitting on an accent fill. Accents hold their light values in dark, so the text on them must not flip either — --ds-text-on-accent on lime, --ds-text-on-accent on Open Blue. Reaching for the plain token puts near-white text on a light fill, about 1.3:1.
  5. Set the page's own background and text from tokens. An inherited colour from a platform preset or a third-party stylesheet cannot flip, and it will not announce itself. Trap 3
  6. Do not use color-scheme to force a mode. It governs browser-rendered widgets only — scrollbars, form controls — and does nothing to any stylesheet's prefers-color-scheme rules. Use data-theme. Rules
  7. Scope a demo that must show one mode. Put data-theme on the demo's own container, not on the page. Pages should follow the reader. Scoping
  8. If anything can set data-theme, mirror the dark block under the attribute as well as the media query — including inherited code you did not write. Why the attribute, not the toggle
  9. Verify computed styles in both modes, and measure contrast. Do not trust the cascade and do not judge by eye. Check the states a reader can actually reach: OS dark, OS light, and the attribute forced either way.

The mechanism

Dark values live in one @media (prefers-color-scheme: dark) block at the end of each stylesheet, keyed to the OS setting. Any page can opt out and lock to light, which is what a page whose job is to show light-mode rendering needs — colour specimens, side-by-side comparisons, this page's own panels:

<html lang="en" data-theme="light">   <!-- locks this page to light -->
  • Tokens flip; components consuming tokens flip for free. Never write a dark hex into a page.
  • Accent colors hold in both modes: Access Lime and Open Blue stay themselves. Text sitting on an accent fill therefore must not flip either — use --ds-text-on-accent on lime, and --ds-text-on-accent on Open Blue. Reaching for plain --ds-text puts near-white text on a light blue fill in dark mode, about 1.3:1.
  • Anything that uses color to carry meaning keeps its second cue (icon, word, position) in dark mode too — the WCAG 1.4.1 requirement applies in both modes.

Keying dark to the attribute as well as the OS

The OS preference is the default and covers most readers, but dark also has to win on a light-OS machine whenever something sets data-theme="dark", so the public stylesheet mirrors the same declarations under an explicit attribute. The trigger is the attribute, not a toggle: inherited code sets it too. The HTML paper mockup has no toggle of its own, yet the ar5iv reader it builds on ships a theme control that writes ar5iv_theme to localStorage, and a bootstrap script turns that into the attribute. Keying only to the media query left a reader who picked dark there on a light-OS machine with a dark canvas and light tokens. If a page can ever carry the attribute, mirror the block:

<html data-theme="dark">    <!-- forces dark regardless of the OS -->
<html data-theme="light">   <!-- forces light, and opts out of the @media block -->
<html>                      <!-- no attribute: follow the OS -->

The mirror is generated from the @media block and must stay identical to it — python3 verification/check-drift.py fails if the two disagree, on both stylesheets. Until 2026-09-16 only tier 1 had a mirror at all, so an internal tool followed the machine and could not be switched: an asymmetry that was inherited rather than chosen.

The control

One control, identical on both surfaces, because a reader who learns it on arxiv.org should not have to learn it again in a moderation queue. It ships as .ds-theme-toggle plus theme.js, and every page under docs/ carries it.

<!-- in the head, NOT deferred -->
<script src="theme.js"></script>

<!-- in the header bar -->
<button type="button" class="ds-theme-toggle"></button>
<span id="ds-theme-status" class="is-sr-only" role="status"></span>
  • Three states, not two. Follow the system, always light, always dark — and follow the system is the default a reader has to be able to get back to. A two-way switch cannot express it, so the first touch would lose the machine's setting for good. That is also why it is a <button> cycling a value rather than the switch, which means on or off.
  • It says its state in words as well as an icon. An icon alone leaves the reader guessing whether the moon means “it is dark” or “make it dark”, which is the commonest failure of this control on the web.
  • The script is not deferred, and that is load-bearing. The attribute has to be on <html> before the first paint or the page renders light and then flips — worst for exactly the reader who chose dark because light hurts. check-policies.py fails on a page that defers it.
  • The button's name does not change when the theme does. The name of a control is what it does, and it is still the theme control; the result goes to the live region, which says “Theme is now dark”. Same rule as the copy button and the switch.
  • Without JavaScript there is no button and the page follows the OS. The control is an addition, never the only route to a readable page.
  • Why a control at all, when the standing preference is to honour OS-level signals rather than offer in-product settings: an OS setting is one choice for a whole machine, and reading is per-context — the same laptop at night in a bright room, a shared library machine whose OS the reader does not control. It stays one control, not the first item of a settings page.

Traps that only show up on a real page

Three ways a token-driven page still comes out wrong in dark mode. All three were found building the blog, which is the first arXiv site to run dark end to end.

Trap What goes wrong What to do
A token that fills a large field Tokens whose dark value is a text accent go pale — Archival Blue flips to a light blue meant for headings. Painted across a masthead, the field washes out. Pin the literal value and say why in a comment, the way the accent colors are pinned. An identity field is a fixed-role color, not a flipping one.
A fill that equals the canvas Warm Wash is a pale tint in light and is the canvas in dark. Anything filled with it — placeholder blocks, quiet panels — disappears in dark mode. Fill raised things with --ds-surface, which is white in light and a lifted surface in dark. Reserve the wash for the page itself.
Text color set outside the tokens A platform preset or inherited color (a theme's global text setting, an inline style) cannot flip, so body text stays dark on a dark canvas. Set body color and background from tokens, and let everything inherit. Check computed styles rather than trusting the cascade.

The toggle control, when a site adds one

The system ships no toggle UI, and most sites should not add one — the OS preference is already the reader's answer. When a site does need one, follow the shape the blog uses, which matches info.arxiv.org: a single bare icon in the header showing the current state, cycling light → dark → auto on click. Three states, not two, so a reader can always get back to "follow my system." Hide the control entirely without JavaScript: the OS preference still applies, so nothing is lost, and a control that does nothing is worse than no control.

Rules

Never hand-pick dark values into a light page

Dark tokens flip automatically with the OS, or not at all. If a demo needs a fixed mode, put data-theme on the demo's own container rather than locking the whole page — and if you do lock a page, check that nothing rewrites it. A static attribute in the markup is not a lock if a script on the page sets the attribute at load.

  • Component CSS consumes tokens — never a literal dark hex.
  • color-scheme: light does not lock a page to light. It governs browser-rendered widgets — scrollbars, form controls, the default canvas — and does nothing to any stylesheet's prefers-color-scheme rules. A page that tried to force light this way still had a third-party stylesheet paint a dark canvas underneath its light tokens. Use data-theme="light" to opt out.
  • A page that deliberately previews dark (like this one's panel, or the alert references) scopes its overrides locally and says so in a comment.
  • Scope the demo, not the page. Documentation pages follow the reader's OS preference — a design system that documents dark mode while refusing to render in it is not much of an argument. A demo that must show a particular mode declares it on its own container instead: <div data-theme="light">. Tokens are declared on any element carrying the attribute, not only on the root, and custom properties inherit, so the nearest ancestor with data-theme wins. Nesting works in both directions: a dark sample inside a light panel inside a page following the OS renders correctly, and the order of the blocks in the stylesheet does not matter.
  • What still does not scope: the six dark button constructions key on the attribute as an ancestor, so they follow an island correctly, but any future component rule must do the same deliberately. And a colour specimen — a chip whose subject is the value itself — is pinned to a literal and never scoped, because it documents one specific value. Four chips on the colour page were painted with tokens and flipped; fixed 2026-08-17.
