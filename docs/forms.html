Forms & validation

A field is a label, a control, optional help text, and a slot for an error. That order never changes. .ds-field lives in both stylesheets, so the same markup works in staff tools and on the public site — only the accent color differs.

A form

Real classes from the public stylesheet. Labels sit above their controls, each control is only as wide as the content it expects, and related fields group by spacing rather than boxes.

Validation

A field passes through three moments. Design all three, not just the middle one — most of a form’s life is spent in the first.

1 · Before

Dispositions

A form used to have only valid and rejected. Most real validation lands between them: a value that is accepted but may be reviewed, or one arXiv corrected on the author’s behalf. Both need saying, and neither is an error.

Error · blocks

Remove the HTML markup <br>.

Warning · proceeds

This does not look like an ACM code. Expected form: F.2.2.

Info · already fixed

Extra spaces were removed. Please confirm it reads correctly.

The note tier is what makes automatic correction legitimate. Normalising whitespace or stripping markup is an edit to author-submitted content; what makes that acceptable is that the author sees the change before it is committed. The review step is not a nicety to drop later for “obvious” fixes.

Several problems on one field

One problem renders as a paragraph. Two or more render as a numbered list — the count is checkable against the summary, and “the second one” has to be sayable while someone works through them. The control shows the worst tier present: a field holding an error and a warning is a field you cannot proceed past.

One control, four problems, two tiers

  1. Do not begin the abstract with the word “Abstract”.
  2. Remove the HTML markup <br>.
  3. Font commands are not processed and appear literally.
  4. Add a space between a URL and the punctuation after it.
Relevant classes
.field-messagesAn <ol> when one field carries several problems. Each <li> takes its own tier class.

Validation summary

On a form of any length, repeat the problems above the first field. This is not a new component — it is .ds-alert with an ordered list of links inside. One alert per severity, never a mixed one: red has to mean “you cannot proceed,” and a non-blocking item inside a red alert destroys that. The heading carries the count, the body says what the tier means, and every row names its field.

2 blocking errors

Blocking errors must be corrected before you can continue. Select an item to jump to that field.

  1. Abstract — do not begin with the word “Abstract”
  2. Abstract — remove the HTML markup <br>

2 warnings

You may continue with warnings, but the submission may be delayed. Select an item to jump to that field.

  1. Abstract — font commands appear literally
  2. ACM classification — not a recognised code

Derive every count and every row from the field results. A summary written by hand can disagree with the fields it describes, and eventually will. Rows repeat the field name even when several name the same field — without it the reader cannot tell whether three problems mean one field to visit or three.

Tone

The general rules — no contractions, one instruction per sentence, the same word for the same thing every time, no idiom in text someone reads while something is going wrong — live in STYLE.md and are not repeated here. What follows is specific to validation messages.

Error
Say what to do, not what went wrong. Never blame the reader, never use invalid on its own, and never make someone guess which of eight rules they broke.
Warning
Say what happens if they continue, because they can. “Your submission may be held for moderator review” is the message; “check this field” is not.
Info
Say what changed and ask them to confirm it. This message exists because arXiv edited the author’s content, so it reports rather than instructs, and it never implies fault.

Accessibility essentials

  • A real <label for> on every control, visible or sr-only.
  • required and aria-required="true" on anything mandatory. Required fields carry no visual marker, so this pair is the only signal — it is not optional.
  • Every message needs an id, and its control needs aria-describedby pointing at it. Without that a screen reader announces the field and nothing else.
  • aria-invalid="true" on the control for the error tier only. A warning is not invalid, and a note is not a problem at all.
  • Every tier states itself in text as well as colour — a visually hidden “Error:” or “Warning:” prefix, or the word in the message. Colour and a border are never the only signal (WCAG 1.4.1).
  • Prefer aria-disabled over disabled for a control that could explain itself. disabled leaves the tab order entirely, so a user who cannot proceed finds nothing there and no reason why. The two must look identical.

Easy to get wrong Setting display: flex on an <li> replaces display: list-item and the marker silently disappears — taking the list semantics with it in some screen readers, so the count is never announced. And aria-describedby must point at something present in the accessibility tree: a tooltip toggled with hidden leaves the control undescribed exactly when it is not being hovered. Keep the description in a visually hidden element, written from the same string.

Layout

  • Labels go above the control. A label-left, field-right layout gives a ragged edge, reads badly on a phone, and makes it easy to ship a control with no label at all.
  • Width follows the content. A field the width of a postcode says what is expected before anyone types. Stretching every control edge-to-edge throws that clue away.
  • Group with spacing and a small heading, not boxes or borders. If spacing cannot hold two groups apart, they probably want to be separate pages.
  • The action bar is right-aligned, primary last. On a long form, repeat it at the top so nobody has to scroll to save.
  • Disabled, not missing. An action that is unavailable renders disabled, so the reader can see it exists and reason about why.

Controls that belong to staff tools

Segmented controls, toggle switches, and filter dropdowns are documented on internal form styles. They are internal-only today because nothing on the public site has needed them yet — not because they are forbidden there.

Usage

<div class="ds-field ds-field--md"> <label class="ds-label" for="email">Email address</label> <input class="ds-input" id="email" type="email" required aria-required="true" aria-describedby="email-hint email-err"> <p class="ds-hint" id="email-hint">Used only to confirm your submission.</p> <p class="field-error" id="email-err" hidden>Enter an email address, like name@university.edu.</p> </div> <!-- On failure: add .is-invalid to the control, unhide the error --> <label class="ds-check"> <input type="checkbox"> <span>Email me when the moderators respond</span> </label>
