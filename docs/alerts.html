Alerts & messaging

How arXiv talks to people when something needs saying: the .ds-alert status banner (success / info / warning / error), the site-wide announcement band, and inline form errors. Every state pairs a distinct icon shape with a leading word, so meaning never rides on color alone (WCAG 1.4.1). Per-context references: public · internal.

The four states

Rendered live from public/design-system.css. Choosing a state is choosing a tone: info is neutral and calm, warning is advisory amber — "worth knowing, nothing broke" — and error is reserved for something actually failing. Do not escalate: an old paper version is a warning, not an error.

Placement

Time-critical messages live in the main reading column where every reader meets them. As an example, on the HTML papers page the warning when viewing an older version sits under the title in the main content area, while the full version history lives in the sidebar accordion.

Never put a timely message into a sidebar where users might miss it, only in the main content area.

We also cannot expect a user to scroll up or down to catch a timely message. It either needs to appear in the area where they are working, or the page needs to scroll them to the area where the message appears.

Semantics & markup

role="status" for success/info (polite — announced when the screen reader is idle); role="alert" for warning/error (assertive — announced immediately). Icons always carry aria-hidden="true"; the leading title word carries the meaning.

<div class="ds-alert ds-alert-warning" role="alert">
  <svg class="ds-alert-icon" viewBox="0 0 24 24" stroke-width="2"
       stroke-linecap="round" stroke-linejoin="round" aria-hidden="true"><!-- Lucide icon paths --></svg>
  <div class="ds-alert-content">
    <p class="ds-alert-title">You are viewing version 1</p>
    <p>A newer version is available — <a href="…">version 3</a>.</p>
  </div>
</div>

The stroke attributes on the <svg> are load-bearing, not boilerplate: Lucide draws each "!" or "i" dot as a 0.01-unit path that only renders with stroke-linecap="round". Copy the icon element whole — without these attributes it renders as an empty hairline outline (a mockup shipped exactly that, 2026-07).

Announcement band

Site-wide, minimal, and time-bound (DESIGN-POLICIES, Banner): a small glyph, one short sentence, one link, a dismiss button. Dismissal persists — the banner never returns for that user, so page function must not depend on it. It sits above the site header as part of the approved header unit; full demo on the header reference page.

Alert vs. announcement

An alert belongs to the page's content ("this PDF failed", "this version is old"). The announcement band belongs to the site — one message for everyone, temporal, dismissable. If a message must persist or is about the current paper, it is an alert.

Errors in forms

Validation messages are the smallest messaging pattern, shared across public and internal (.is-invalid / .field-error / .field-required). The error text is linked to its field with aria-describedby; the border color change is never the only signal.

Enter a complete email address, like name@institution.edu.

  • Say what to do, not what went wrong internally. "Enter a complete email address" beats "Validation failed."
  • Required fields get the visible asterisk AND required + aria-required="true".
  • Error text uses the error foreground token — 8.6:1 on white, AAA — with an icon, not color alone.

Writing the message

  • Title = the situation, body = what to do. "Could not load the PDF" / "Try the HTML version instead."
  • Offer the way forward as a link inside the body whenever one exists.
  • Match arXiv's voice: plain, direct, no exclamation marks, no blame ("the file failed to render", not "you uploaded a bad file").
  • One row when possible. The older-version warning is one compact row; alerts should not crowd out the content they annotate.
