Alerts & messaging

How arXiv talks to people when something needs saying: the .ds-alert status banner (success / info / warning / error), the site-wide announcement band, and inline form errors. Every state pairs a distinct icon shape with a leading word, so meaning never rides on color alone (WCAG 1.4.1).

The four states

Rendered live from design-system.css. Choosing a state is choosing a tone: info is neutral and calm, warning is advisory amber — “worth knowing, nothing broke” — and error is reserved for something actually failing.

  <svg class="ds-alert-icon" viewBox="0 0 24 24" stroke-width="2"
       stroke-linecap="round" stroke-linejoin="round" aria-hidden="true">
    <!-- Lucide icon paths -->
  </svg>
  <div class="ds-alert-content">
    <p class="ds-alert-title">You are viewing version 1</p>
    <p>A newer version is available — <a href="…">version 3</a>.</p>
  </div>
</div>
.ds-alert
The container. Always used with one of the four state classes, never alone. Takes role="status" for success and info, role="alert" for warning and error.
.ds-alert-success, -info, -warning, -error
The state: .ds-alert-success, .ds-alert-info, .ds-alert-warning, or .ds-alert-error. Sets the background, border, and text colour from the status tokens. The same four classes and the same colours on both surfaces.
.ds-alert-icon
The icon, an inline SVG with aria-hidden="true". Each state has its own shape: a check, an “i”, a triangle, an “x”. Copy the icon element whole, attributes included: Lucide draws each “!” or “i” dot as a 0.01-unit path that only renders with stroke-linecap="round". Without these attributes it renders as an empty hairline outline.
.ds-alert-content
Holds the text. One or more <p> elements; a link inside it takes the alert’s own colour.
.ds-alert-title
The leading line, in bold. It names the situation, and it is what carries the meaning for a reader who cannot see the icon or the colour. Optional on a one-line alert.

.ds-close
The dismiss control, documented on Buttons. Put it last inside .ds-alert; the alert positions it at the end of the first line and it takes the alert’s colour. Removing the alert from the page is the host’s job: the stylesheet gives the control no behaviour.
.is-sr-only
Required inside the control. The icon is aria-hidden, so without this span the button announces as “button” and nothing more.

Internal variant

Nothing about the component changes on the internal surface: the status palette is shared, so an error is the same red in the moderation queue as on a paper page. What changes is what the messages are about, and these four are here because the wording is the part worth copying.

.ds-internal
On a parent, or on <html> for a whole internal page. The alert classes are the same and the status tokens do not change, so the alert looks the same; the wrapper is what makes the buttons and links around it internal.

A queue message still says what to do next “Action failed” on its own leaves a moderator with nowhere to go. Every one of the four above ends in either a next step or a link to the thing that explains it — the same rule as the public side, and the one most easily dropped when the reader is a colleague.

Announcement band

Site-wide, minimal, and time-bound (DESIGN-POLICIES, Banner): a small glyph, one short sentence, one link, a dismiss button. Dismissal persists — the banner never returns for that user, so page function must not depend on it. It sits above the site header as part of the approved header unit; full demo on the header reference page.

.ds-announcement
The band. Takes role="region" and an aria-label so a screen reader user can find it and skip it. Goes directly above .ds-site-header.
.ds-announcement-glyph
The icon, an inline SVG with aria-hidden="true".
.ds-announcement-text
The one sentence.
.ds-announcement-link
The one link. An <a> with a real href.
.ds-close
The dismiss control, last inside the band; the band positions it at the right edge. Remembering the dismissal is the host’s job.

Alert or announcement

An alert belongs to the page’s content (“this PDF failed”, “this version is old”). The announcement band belongs to the site — one message for everyone, temporal, dismissable. If a message must persist or is about the current paper, it is an alert.

Errors in forms

Validation messages are the smallest messaging pattern, shared across public and internal (.is-invalid / .field-error). The error text is linked to its field with aria-describedby; the border color change is never the only signal. The full pattern, with warning and info messages, is on Forms.

Relevant code 
<div class="ds-field">
  <label class="ds-label" for="email">Email address</label>
  <input class="ds-input is-invalid" id="email" type="email"
         required aria-required="true" aria-invalid="true"
         aria-describedby="email-err" value="shamsi@example">
  <p class="field-error" id="email-err">Enter a complete email address, like name@institution.edu.</p>
</div>
.ds-field, .ds-label, .ds-input
The field, its label, and its control, as on Forms.
.is-invalid
On the control, for the error state. Pair it with aria-invalid="true".
.field-error
The message, after the control. Needs an id, named in the control’s aria-describedby. Keep it hidden until it applies.
required, aria-required
Both on the control. A required field is not marked in the visible label on a public form; only an optional one is, with the word “(optional)”.

Accessibility essentials

  • Choose the role by state. Put role="status" on a success or info alert: it is polite, and a screen reader announces it when idle. Put role="alert" on a warning or error alert: it is assertive, and a screen reader announces it immediately. Do not use role="alert" for anything that can wait.
  • Say the state in words. The icon is aria-hidden="true" and the colour is invisible to a screen reader, so the title or the first words of the message must carry the meaning: “Could not load the PDF”, not “Oops”.
  • Name the dismiss control. The .ds-close button needs a <span class="is-sr-only"> that says what it dismisses, such as “Dismiss this message” or “Dismiss announcement”. Do not use title or aria-label for this, because page translation tools skip attributes.
  • Put focus somewhere after a dismiss. Removing the alert removes the focused button with it. Move focus to the element just before where the alert was, so a keyboard user is not dropped back to the top of the page.
  • Link a form error to its field. Give the .field-error an id, name it in the control’s aria-describedby, and set aria-invalid="true" on the control. The red border on its own tells a screen reader user nothing.

Rules

Placement

Time-critical messages live in the main reading column where every reader meets them. As an example, on the HTML papers page the warning when viewing an older version sits under the title in the main content area, while the full version history lives in the sidebar accordion.

Never put a timely message into a sidebar where users might miss it, only in the main content area.

We also cannot expect a user to scroll up or down to catch a timely message. It either needs to appear in the area where they are working, or the page needs to scroll them to the area where the message appears.

Writing the message

  • Title = the situation, body = what to do. “Could not load the PDF” / “Try the HTML version instead.”
  • Offer the way forward as a link inside the body whenever one exists.
  • Say what to do, not what went wrong internally. “Enter a complete email address” beats “Validation failed.”
  • Match arXiv’s voice: plain, direct, no exclamation marks, no blame (“the file failed to render”, not “you uploaded a bad file”).
  • One row when possible. The older-version warning is one compact row; alerts should not crowd out the content they annotate.
