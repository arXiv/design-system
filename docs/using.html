Using the design system

Which files to link, in what order, what the two tiers mean, and the handful of things that go wrong if you guess. Everything else in these docs answers “what should this look like”; this page answers “how do I get it”.

A page, start to finish

This is the whole of it for a public arXiv page. Copy it, then put your content where the comment is.

<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Your page &mdash; arXiv</title>

  <link rel="stylesheet" href="fonts.css">
  <link rel="stylesheet" href="design-system.css">
  <script src="theme.js"></script>
</head>

<body class="ds-page">
  <div class="ds-container">
    <!-- every direct child here is one section -->
  </div>
</body>
</html>
  • fonts.css before design-system.css. The stylesheet names the faces; the font file declares them. Either order renders, but this one matches every page in the repo, and consistency is the point of a template.
  • theme.js is not deferred, and that is deliberate. It writes the reader's theme onto <html> before the first paint. Add defer and the page renders light and then flips — worst for exactly the reader who chose dark because light hurts.
  • class="ds-page" on the body is not optional. The foundation — the type stack, the canvas colour, box-sizing, the base heading and list rhythm — is scoped to it, so a page without it gets components on unstyled ground.
  • .ds-container is the page shell. See below; it does more than centre things.

If you are building an internal tool

One class on <html>, and two files, in this order, and never only the second one.

<html lang="en" class="ds-internal">
…
<link rel="stylesheet" href="../fonts.css">
<link rel="stylesheet" href="../design-system.css">    <!-- tier 1 -->
<link rel="stylesheet" href="internal-tools.css">      <!-- tier 2 -->
<script src="../theme.js"></script>

The one mistake to avoid

internal-tools.css is not a standalone stylesheet. It holds only what that surface alone has — tables, metadata panels, info cards, the internal icon-button variants, and the tokens whose values change. Load it on its own and you get those components on no foundation at all.

  • The accent is the whole mechanism. .ds-internal re-points --ds-accent and its family to Access Lime, and every component inside it that reaches for the accent follows without being told. It works on any parent, so a page that shows both surfaces puts it on a wrapper instead of on <html>. That is why there is no second copy of the button, the tag or the switch.
  • Never copy a component into tier 2 to restyle it. If it needs to look different on your surface, that is a token, not a second copy. A component that exists twice disagrees with itself within about a month — we have the commits.
  • The two accents are never crossed. Access Lime means internal tools, Open Blue means the public site, and the accent answers where am I. A privileged control on a public page stays Open Blue — see DESIGN-POLICIES.

What .ds-container does

It is three grid tracks, not a max-width, and the difference matters in two places.

  • It owns the space between sections. Every direct child is a section and the gap between them comes from the container, because a section cannot know what follows it and so cannot know how far away that should be. Do not add top or bottom margins to sections — the container already did.
  • A band that runs edge to edge gets .ds-full and spans the outer track. No negative margins, and above all no viewport units: 100vw includes the scrollbar while the document width does not, so a calc(-50vw + 50%) band overhangs and the page scrolls sideways. That is invisible on a Mac with overlay scrollbars and obvious on Windows, which is why it survives review. We found it in a live mockup at 18px of drift.
  • Its width comes from --ds-width-page and --ds-gutter. Change the page width by re-pointing one token, not by adding a second width beside it.
<div class="ds-container">
  <section>…</section>                   <!-- content track -->
  <section class="ds-full">…</section>    <!-- edge to edge -->
</div>

Five things that go wrong

Each of these has happened in this repository, and each one is now caught by python3 verification/check-policies.py. Run it before you push.

  1. Loading a font or a script from someone else's server. Everything is self-hosted. No Google Fonts, no CDN. If an existing page does it, that page is wrong.
  2. Writing a size in px. Type sizes are rem, and a control's padding is em against its own label, so the whole control grows when a reader raises their font size. A fixed box around growing text is the same failure as never growing at all.
  3. Using a var() that does not exist. CSS drops the entire declaration, silently. A component of ours shipped with no padding for a day that way.
  4. Typing the wordmark. The arXiv logo is a drawn mark in assets/images/logos/, never the letters “arXiv” in a heading.
  5. Inventing a colour. If you need one that is not in the palette, that is a conversation, not a hex value. Two surfaces already share one palette and a third value is how that stops being true.
