Shamsi: what is off
Read

This build chose page zones as a content organization mechanism, but that pushed the main content below the fold on my laptop screen. That organization method is probably not the right choice for dense screens like the moderation activity dashboards.

This build used a table to organize each group/category. It is a data rich choice, but what it misses out on is clearly signaling that this is a portal page for clicking into each group. The table somehow makes me feel like this is the main data and action page and I don't cognitively expect to see a lot more data and choices when I click in. The use of cards would do a better job signaling that this is a doorway page and the main action is just clicking on a card for more. Perhaps the spec make it sound like the data must be displayed, but I had made it clear that we could put placeholder content wherever data visualizations will appear in the future. I don't want the agents distracted by the data. I want to evaluate wether agents are successfully identifying primary content and I want to see how they prioritize and organize content. The rich data will be a distraction. That is a visualization challenge for another time.

The table really does not work with mobile view. We should decide if mobile view is something we drop for these tests.

Using an alert to signal which groups need attention is a less efficient choice than showing the groups in cards and highlighting the cards that need attention. With an alert, I need to read it, and remember the group name, scroll down, and locate it in a table.

The "refresh" button seems too prominent for what it does. It was given the primary button style, but that is not the primary action on this page.

I am confused why "staff reports" is a text-only link and not a button. Also, it's location is inconvenient because it pushed the main content down further.

What is the purpose of the "staff only" pill? Is it supposed to signal that this is a staff page? I don't think that is necessary. Each logged in viewer will have their content filtered based on their access level. They don't need to be told that they are a staff or a moderator.

The dates description also pushes the content down further. I would like an agent to do a better job of identifying the primary content and then ensure secondary and tertiary content does not get in the way.

Lastly, for the header, this agent chose a modified light header version and it also does not contain the standard header content. I wonder why. It is not necessarily a terrible choice, but unless we specify a modified header I would expect an agent to understand that using the standard header is the default.

The staff reports page is confusing to me. First, the name "staff reports" already signals it is for staff. Then there is a lozenge added to the intro paragraph telling me again that it is only for staff. And then the reports table tells me again who can see it. Also, the agent again used a table instead of cards, even though this page is a portal to action pages adn not an action page in itself. A table make me think that I will be working and taking action on this page, while cards do not carry that connotation.

Shamsi: notes after seeing them together

All of the builds needed a better analysis of the true hierarchy of the content. And all of them spent too much effort organizing the provided rich data (they all chose tables), and not enough effort understanding the structure these pages need. This is a complex challenge in terms of content hierarchy and organization. I think it would take a human quite a bit of thought and different attempts. All of the agents failed at coming up with a healthy hierarchy and content organization plan.

What the builds had in common

  • All four used .ds-internal, the light header, .ds-card--stat for totals, tables for the two doorway pages, an alert for groups that need attention, and chart placeholders as asked.
  • No build used .ds-tabs. Two put parts and views in sidebar accordions; two used .ds-subnav for the parts and a row of links or a second .ds-subnav for the views.
  • All four put status lines, refresh and alerts above the main content.
  • Design-system bugs: .ds-table-scroll was not positioned, so is-sr-only text in sortable headers widened the page (fixed); .ds-card-grid's 20rem minimum (fixed 2026-10-07).
  • Predictions: 1 right (all .ds-internal). 2 right (all four used .ds-card--stat). 3 partly: they split, but between sidebar accordions and secondary navigation, not tabs.
